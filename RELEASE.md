# Чек-лист первого релиза (1.0.0)

Файл делится на две части: что уже проверено при подготовке релиза и что должны проверить вы на своём компьютере и на сервере. Вторая часть обязательна: часть проверок невозможно выполнить без Docker, браузера и настоящего сервера.

## Часть 1. Что проверено при подготовке

Проверки выполнялись в облачной среде на настоящем PostgreSQL 16.

| Область | Результат |
| --- | --- |
| Backend, автоматические тесты (`pytest`) | пройдены; включая сквозной сценарий (регистрация → семья → расписание → продукты → нормы → план недели → закупки → семейное меню → фото → финансы) и проверку, что все эндпоинты, кроме перечисленных публичных, требуют входа |
| Проверка тестов на чувствительность | в защитную логику вносились намеренные поломки (мутации): тесты их ловили; найденные пропуски закрыты новыми тестами |
| Миграции Alembic | цикл вверх → вниз → вверх и сверка модели с базой без расхождений |
| Frontend, проверка типов (`tsc`) | без ошибок |
| Сессии на frontend и service worker | поведение проверено скриптами Node с имитацией окружения |
| Скрипты резервных копий | копия, блокировка, ротация, восстановление с проверкой данных до и после, повреждённый файл, неверная контрольная сумма, `test-restore`, `check-backup` |
| Конфигурация Docker Compose | синтаксис корректен |

### Что в проверке не участвовало

- Библиотеки `psycopg2` и `pwdlib`/argon2 подменялись упрощёнными заменами; настоящие версии из `requirements.txt` в тестах не запускались.
- Сборка `next build`, ESLint, `pip-audit`, `npm audit`.
- Сборка Docker-образов и запуск контейнеров (в среде нет Docker daemon); права, `read_only`, `cap_drop` и работа Caddy не проверены на практике.
- Реальный браузер и телефон: внешний вид, установка PWA, работа service worker.
- Команды внешнего копирования (`rclone`, `rsync`, `gpg`) и настройка группы `nutribackup`.

## Часть 2. Что проверить вам

### A. На своём компьютере (перед сервером)

1. Сделайте копию базы (на случай, если миграция что-то изменит):
   ```powershell
   pg_dump -U nutrition -Fc -f nutrition-before-1.0.dump nutrition
   ```
2. Установите зависимости и проверьте тесты:
   ```powershell
   cd backend
   pip install -r requirements.txt
   pytest -v
   ```
   Ожидание: все тесты зелёные. Любой красный тест — повод остановиться и показать мне вывод.
3. Примените миграции:
   ```powershell
   alembic upgrade head
   alembic current          # должна быть ревизия dd2eb071704c (head)
   ```
4. Проверьте frontend:
   ```powershell
   cd ..\frontend
   npm install
   npx tsc --noEmit
   npm run lint
   npm run build
   ```
   `npm run build` — самая важная проверка: она показывает ошибки, которые я не смог поймать без сборки.
5. Запустите оба сервера и пройдите вручную:
   - вход и выход; повторный вход; обновление страницы не разлогинивает;
   - смена пароля в профиле (старые сессии должны завершиться);
   - создание записи в каждом разделе: расписание, продукты, нормы, план недели, закупки, семейное меню, фото, финансы;
   - загрузка фото больше лимита (должна быть понятная ошибка).
6. Проверьте на телефоне в одной сети с компьютером (или после выкладки на сервер): интерфейс помещается в экран, кнопки нажимаются, нижняя панель не перекрывает содержимое.

### B. Docker на своём компьютере

1. `copy .env.example .env` и заполните два значения.
2. `docker compose up -d --build`, затем `docker compose ps`: все службы `running`, у backend `healthy`.
3. Откройте <http://localhost:3000>, зарегистрируйтесь, добавьте данные.
4. `docker compose down` и снова `docker compose up -d`: данные на месте (тома).
5. Если что-то не сходится, пришлите вывод `docker compose logs backend --tail 50`.

### C. Публичный сервер

Выполняйте по [deploy/README.md](deploy/README.md) и отмечайте пункты:

- [ ] Сервер подготовлен (отдельный пользователь, вход по ключу, файрвол 80/443/SSH, автообновления).
- [ ] DNS указывает на сервер.
- [ ] `deploy/.env` заполнен, `./deploy/check-env.sh` не выдаёт ошибок.
- [ ] `./deploy/deploy.sh` завершился успешно, сайт открывается по `https://` с действительным сертификатом.
- [ ] Все проверки из раздела 7 файла `deploy/README.md` дают ожидаемый результат: `/api/health` отвечает `{"status":"ok"}`, `/api/docs` и `/api/openapi.json` закрыты (404), `/api/users/me` без входа даёт 401, снаружи открыты только порты 22, 80 и 443.
- [ ] Вход работает, после обновления страницы сессия сохраняется.
- [ ] Вы и семья зарегистрированы, затем `REGISTRATION_OPEN=false` и `./deploy/deploy.sh`.
- [ ] Первая резервная копия появилась (`./deploy/backup/check-backup.sh`).
- [ ] `./deploy/backup/test-restore.sh` завершился строкой `OK`.
- [ ] Настроена копия за пределами сервера (раздел 4 файла [deploy/BACKUP.md](deploy/BACKUP.md)) и оповещение о сбое.
- [ ] Сохранены вне сервера: содержимое `deploy/.env`, пароли шифрования копий.
- [ ] PWA установлена на iPhone: Safari → «Поделиться» → «На экран Домой»; приложение открывается без адресной строки.
- [ ] Внешняя проверка заголовков, например на <https://securityheaders.com> (ожидание: высокая оценка; замечание про `unsafe-inline` в CSP известно).

### D. После запуска (первые недели)

- Раз в месяц: `test-restore.sh`.
- Раз в месяц: `docker compose pull` для базовых образов и пересборка (`./deploy/deploy.sh`) ради обновлений безопасности; `apt upgrade` на сервере.
- Следите за свободным местом: `df -h` (копии и фото занимают место).
- Если в журнале (`docker compose logs backend`) много строк о неудачных входах с одного адреса, это попытки подбора пароля; ограничения их остановят, но можно закрыть адрес в файрволе.
