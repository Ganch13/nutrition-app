# Резервные копии

Все данные семьи (питание, вес, тренировки, финансы, фото прогресса) лежат в двух местах: в базе PostgreSQL и в папке с фото. Если сервер сломается, диск откажет или данные случайно удалят, вернуть их можно только из копии. Копия, которая лежит на том же сервере, защищает от ошибки и поломки программы, но **не защищает от потери сервера**, поэтому её нужно ещё и вынести за его пределы (раздел 4).

## 1. Что делается автоматически

Служба `backup` (в `deploy/docker-compose.prod.yml`) каждый день в `BACKUP_TIME` (по умолчанию 03:30 по времени `TZ`) создаёт в папке `BACKUP_DIR` (по умолчанию `/var/backups/nutrition`) три файла с одним временем в имени:

| Файл | Что внутри |
| --- | --- |
| `nutrition-db-2026-10-27_033000.dump` | вся база данных (формат `pg_dump`, уже сжат) |
| `nutrition-photos-2026-10-27_033000.tar.gz` | фото прогресса |
| `nutrition-2026-10-27_033000.sha256` | контрольные суммы двух файлов (проверка, что файл не повреждён) |

Меры надёжности:

- Копия пишется во временный файл и принимается, только если архив читается и в нём есть таблицы. Оборванная или пустая копия не сохраняется и не заменяет хорошие.
- Файлы доступны только владельцу и группе `nutribackup` (права 640), посторонним пользователям сервера доступа нет.
- Первая копия делается сразу при запуске службы, если свежих нет, чтобы сервер не оставался без защиты до первой ночи.
- Хранение: ежедневные копии за **14 дней**, копии первого числа каждого месяца за **6 месяцев**, три самые свежие копии хранятся всегда. Сроки меняются в `deploy/.env` (`KEEP_DAILY_DAYS`, `KEEP_MONTHLY_MONTHS`). Место: типичная копия занимает единицы мегабайт плюс размер фото, и их общий объём на диске стоит оценить после первых недель использования.
- Служба `backup` помечается `unhealthy` в `docker compose ps`, если свежей копии нет больше 26 часов.

## 2. Как убедиться, что копии делаются

```bash
ls -lh /var/backups/nutrition                      # на сервере: должны быть свежие файлы
./deploy/backup/check-backup.sh                    # «Хорошо: последняя копия ... N ч. назад»; код возврата 0
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env logs --tail 20 backup
```

Сделать копию вручную (например, перед рискованными действиями):

```bash
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env exec -T backup bash /backup/backup.sh
```

### Доступ к копиям без sudo (один раз)

Файлы копий принадлежат служебному пользователю 10001, поэтому обычному пользователю `deploy` они недоступны. Дайте ему право чтения через группу (после команды нужно выйти из SSH и войти снова):

```bash
sudo groupadd -g 10001 nutribackup
sudo usermod -aG nutribackup deploy
```

После этого `ls`, `check-backup.sh`, `scp` и `rsync` работают от имени `deploy`; другие пользователи сервера доступа не получают.

### Оповещение о сбое

Чтобы сбой не остался незамеченным, вызывайте `check-backup.sh` по расписанию и подключите оповещение. Вариант без собственной почтовой настройки: бесплатный сервис healthchecks.io. Создайте там проверку «каждые 1 день, допуск 6 часов», скопируйте её адрес и добавьте в `crontab -e` (на сервере):

```cron
17 * * * *  PING_URL=https://hc-ping.com/ВАШ-КОД /home/deploy/nutrition/deploy/backup/check-backup.sh
```

Пока копия свежая, сервис получает вызов раз в час. Если копии перестали делаться, вызовы прекращаются, и сервис присылает письмо или сообщение в Telegram. После настройки группы (см. выше) `crontab -e` можно выполнять от обычного пользователя `deploy`.

## 3. Проверка восстановления (раз в месяц)

Копия, из которой ни разу не пробовали восстановить, — это гипотеза. Проверка не затрагивает рабочую базу: самая свежая копия разворачивается во временную базу, показываются количества записей, затем временная база удаляется.

```bash
./deploy/backup/test-restore.sh                    # самая свежая копия
./deploy/backup/test-restore.sh /var/backups/nutrition/nutrition-db-2026-10-01_033000.dump
```

Ожидаемый результат: проверка контрольной суммы `OK`, список таблиц с количеством записей (`users`, `households`, `meal_entries`, `progress_photos` и т. д.), версия структуры базы и строка `OK: копия восстанавливается.`

Проверьте, что число пользователей и записей соответствует ожиданиям.

## 4. Копия за пределами сервера

Это самая важная часть. Правило «3-2-1»: три копии данных, на двух разных носителях, одна из них в другом месте. Минимум для нашего случая: ночная копия на сервере плюс копия на другой машине или в облаке.

> В копиях лежат личные данные (вес, питание, фото). Перед отправкой за пределы сервера их нужно шифровать. В примерах ниже это делает `rclone crypt` или `gpg`.

Команды ниже выполняются на сервере по расписанию (`sudo crontab -e`: от `root`, подойдёт и пользователь из группы `nutribackup`). Команды этого раздела не запускались в моей среде проверки, поэтому проверьте первую копию вручную, прежде чем полагаться на расписание.

### Вариант А. Облачное хранилище через rclone

1. Установите: `sudo apt install -y rclone`.
2. Настройте хранилище: `sudo rclone config` (подойдут Backblaze B2, любой S3-совместимый сервис, Яндекс.Диск, Google Drive и др.). Для шифрования создайте поверх него второй ремот типа `crypt` (например, `nutri-crypt`) и **сохраните пароли шифрования отдельно от сервера**: без них копии не прочитать.
3. Добавьте в `sudo crontab -e` (через час после ночной копии):

```cron
30 4 * * *  rclone copy /var/backups/nutrition nutri-crypt:nutrition-backups --max-age 3d --log-file /var/log/nutrition-rclone.log
```

Проверка: `sudo rclone ls nutri-crypt:nutrition-backups` показывает файлы.

### Вариант Б. На ваш домашний компьютер или NAS по SSH (rsync)

1. На сервере создайте ключ только для копий: `sudo ssh-keygen -t ed25519 -f /root/.ssh/backup_key -N ""`.
2. Добавьте содержимое `/root/.ssh/backup_key.pub` в `authorized_keys` на принимающей машине (пользователь, у которого есть право записи в нужную папку).
3. Файлы шифруются перед отправкой, чтобы на принимающей машине не лежали открытые данные:

```cron
45 4 * * *  for f in $(find /var/backups/nutrition -maxdepth 1 -type f -mtime -2 \( -name '*.dump' -o -name '*.tar.gz' \)); do [ -e "$f.gpg" ] || gpg --batch --pinentry-mode loopback --passphrase-file /root/.backup_passphrase --symmetric --cipher-algo AES256 -o "/var/backups/nutrition-offsite/$(basename "$f").gpg" "$f"; done; rsync -a -e "ssh -i /root/.ssh/backup_key" /var/backups/nutrition-offsite/ пользователь@принимающая-машина:/путь/nutrition-backups/
```

Предварительно: `sudo install -d -m 700 /var/backups/nutrition-offsite`, `sudo sh -c 'openssl rand -base64 32 > /root/.backup_passphrase' && sudo chmod 600 /root/.backup_passphrase` и **сохраните фразу** `/root/.backup_passphrase` в менеджере паролей. Расшифровка: `gpg --decrypt файл.gpg > файл`.

### Вариант В. Просто скачивать на свой компьютер

Подойдёт на старте, если ничего из вышеперечисленного не настроено. Раз в неделю с вашего компьютера:

```bash
scp deploy@IP-СЕРВЕРА:/var/backups/nutrition/nutrition-db-*.dump ./
```

Для этого пользователь `deploy` должен входить в группу `nutribackup` (см. раздел 2). Не оставляйте такие файлы на общедоступных носителях.

## 5. Восстановление

Когда это нужно: данные случайно удалены или испорчены, неудачное обновление изменило структуру базы, сервер переустановлен.

### 5.1. Из копии на этом же сервере

```bash
cd ~/nutrition
./deploy/backup/restore.sh /var/backups/nutrition/nutrition-db-2026-10-27_033000.dump \
                           /var/backups/nutrition/nutrition-photos-2026-10-27_033000.tar.gz
```

Второй файл (фото) можно не указывать, тогда восстанавливается только база. Скрипт выполняет по шагам:

1. Проверяет контрольную сумму файлов и спрашивает подтверждение: нужно ввести слово `ВОССТАНОВИТЬ`.
2. **Разворачивает копию во временную базу.** Если файл повреждён, на этом всё заканчивается, рабочие данные не затронуты.
3. Делает резервную копию текущего состояния.
4. Останавливает сайт, переименовывает текущую базу в `nutrition_before_restore_<время>` (**не удаляя её**) и ставит на её место восстановленную.
5. Если указан архив с фото, заменяет содержимое папки с фото.
6. Запускает сайт. При старте backend сам обновляет структуру базы до актуальной версии.

После восстановления откройте сайт и проверьте данные. Когда убедитесь, что всё в порядке, удалите прежнюю базу командой, которую скрипт покажет в конце, чтобы она не занимала место.

Если вы поняли, что восстановили не то, прежняя база всё ещё есть: переименуйте базы обратно или запустите `restore.sh` с предыдущей копией.

### 5.2. На новом (чистом) сервере

1. Выполните шаги 2–5 из [README.md](README.md): подготовка сервера, код, `deploy/.env` (**те же** `POSTGRES_PASSWORD` и `JWT_SECRET_KEY`, что были раньше; если их нет, подойдут новые, пользователи просто войдут заново).
2. Поднимите только базу: `docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env up -d db`.
3. Скопируйте на новый сервер все три файла нужной копии (база, фото, `.sha256`) в любую папку, например `~/restore` (расшифруйте, если шифровали).
4. Запустите `./deploy/backup/restore.sh <файл-базы> <файл-фото>`. Скрипт сам поднимет остальные службы.
5. Проверьте сайт, а затем настройте внешнее копирование (раздел 4) заново.

### 5.3. Что восстановление не возвращает

- Всё, что добавлено после времени создания копии (до суток).
- Сессии: после восстановления из старой копии часть сессий окажется недействительной, и пользователям придётся один раз войти заново. Это нормально.

## 6. Как это устроено (для понимания)

- `backup-loop.sh` — главный процесс службы: ждёт назначенное время и запускает `backup.sh`.
- `backup.sh` — `pg_dump` в формате custom, проверка архива, `tar` фото, контрольные суммы, затем `rotate.sh`. Блокировка не даёт запуститься двум копиям одновременно. База копируется раньше фото: так в копии не бывает записей о фото, которых нет в архиве.
- `rotate.sh` — удаляет устаревшие наборы файлов по правилам из раздела 1. Проверить без удаления: `ROTATE_DRY_RUN=1 BACKUP_DIR=/var/backups/nutrition ./deploy/backup/rotate.sh`.
- `restore.sh`, `test-restore.sh`, `check-backup.sh` — описаны выше.

Во время разработки логика копирования, ротации, восстановления и проверки проверялась на настоящем PostgreSQL 16: успешная копия, отказ при пустой базе и неверном пароле, блокировка, устаревшая блокировка, ротация по датам, восстановление со сверкой данных до и после, отказ при повреждённом файле и при несовпадении контрольной суммы. Запуск внутри Docker-контейнеров и работа с настоящим сервером в этой проверке не воспроизводились.
