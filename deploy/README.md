# Развёртывание на публичном сервере

Это руководство ведёт от «чистого» арендованного сервера до работающего сайта с HTTPS, ежедневными резервными копиями и закрытой для посторонних документацией. Резервным копиям посвящён отдельный файл [BACKUP.md](BACKUP.md).

Если вам нужно запустить приложение просто на своём компьютере или на компьютере друга, публичный сервер не нужен: используйте `docker-compose.yml` из корня проекта (см. основной [README](../README.md)).

## 0. Что получится

```
Интернет ──► Caddy (порты 80/443, HTTPS) ──► /api/*        ──► backend (FastAPI) ──► PostgreSQL
                                         └──► всё остальное ──► frontend (Next.js)

backup (каждую ночь) ──► /var/backups/nutrition  (база + фото, 14 дней + 6 месяцев)
```

- Наружу открыты только порты **80 и 443** (Caddy). База данных, backend и frontend доступны лишь внутри Docker, причём база находится в отдельной сети, до неё не может добраться даже Caddy.
- Сайт и API живут на **одном домене** (`https://ваш-домен/api/...`). Благодаря этому не нужна настройка CORS, а cookie сессии привязана к одному сайту.
- Сертификат HTTPS Caddy получает и продлевает сам (Let's Encrypt), вручную ничего делать не нужно.

## 1. Что понадобится

| Что | Требование |
| --- | --- |
| Сервер (VPS) | Ubuntu 24.04 LTS, от 2 ГБ памяти (при 1 ГБ сборка сайта может падать, см. шаг 2.6), от 20 ГБ диска, публичный IPv4-адрес |
| Домен | Ваш домен или поддомен, например `nutrition.mydomain.ru`. Вы должны иметь возможность добавить в его DNS A-запись |
| Доступ | SSH-доступ к серверу с правами `root` (только для первой настройки) |
| Порты | У провайдера (в «файрволе» панели управления) должны быть открыты 22, 80, 443 (TCP) и 443 (UDP) |

## 2. Подготовка сервера (один раз)

Все команды этого раздела выполняются на сервере. Сначала подключитесь: `ssh root@IP-СЕРВЕРА`.

### 2.1. Отдельный пользователь вместо root

Работать под `root` небезопасно: любая ошибка или взлом получают полный контроль над сервером. Создайте обычного пользователя:

```bash
adduser deploy                       # придумайте пароль, остальные вопросы можно пропустить
usermod -aG sudo deploy
mkdir -p /home/deploy/.ssh
cp ~/.ssh/authorized_keys /home/deploy/.ssh/    # ваш ключ входа (если вы входили по ключу)
chown -R deploy:deploy /home/deploy/.ssh && chmod 700 /home/deploy/.ssh && chmod 600 /home/deploy/.ssh/authorized_keys
```

Если вы входили на сервер по паролю и ключа у вас ещё нет: на своём компьютере выполните `ssh-keygen -t ed25519`, затем `ssh-copy-id deploy@IP-СЕРВЕРА`.

### 2.2. Вход только по ключу

Пароли по SSH подбирают боты круглосуточно. После того как вход по ключу заработает, пароли отключаются.

> **Осторожность.** Не закрывайте текущее окно, пока не проверите вход по ключу из **второго** окна. «Второе окно» — это просто ещё одно окно терминала на вашем компьютере (вторая вкладка PowerShell или второе окно PuTTY), в котором вы заново подключаетесь: `ssh deploy@IP-СЕРВЕРА`. Первое окно остаётся подключённым как запасной ход: если вход по ключу не заработал или вы ошиблись в настройках, вы исправите это из первого окна. Если закрыть единственное окно и потерять вход, придётся пользоваться консолью в панели провайдера.

```bash
sudo tee /etc/ssh/sshd_config.d/00-hardening.conf >/dev/null <<'EOF'
PasswordAuthentication no
PermitRootLogin no
EOF
sudo sshd -t && sudo systemctl reload ssh      # sshd -t проверяет файл настроек; ошибок быть не должно
sudo sshd -T | grep -E '^(passwordauthentication|permitrootlogin)'     # ожидаем: passwordauthentication no, permitrootlogin no
```

Имя файла начинается с `00-` не случайно: SSH берёт первое найденное значение параметра, а файлы читаются по алфавиту. У облачных образов бывает файл `50-cloud-init.conf` с `PasswordAuthentication yes`; наш файл должен идти раньше него. Вторая команда показывает, какие значения действуют на самом деле: если там `yes`, значит какой-то другой файл в `/etc/ssh/sshd_config.d/` перебивает наш (найти его: `sudo grep -ri passwordauthentication /etc/ssh/`).

### 2.3. Файрвол

```bash
sudo apt update && sudo apt install -y ufw
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw allow 443/udp
sudo ufw enable
sudo ufw status
```

Ожидаемый результат: в списке только SSH, 80 и 443.

> Docker сам правит правила сетевого экрана и обходит `ufw` для опубликованных портов. Здесь это безопасно, потому что наш compose публикует только 80 и 443, и именно их мы хотим открыть. Не добавляйте в compose `ports:` для базы и backend.

### 2.4. Защита от подбора пароля SSH и автообновления

```bash
sudo apt install -y fail2ban unattended-upgrades
sudo systemctl enable --now fail2ban             # блокирует адреса, которые много раз ошиблись при входе по SSH
sudo dpkg-reconfigure -plow unattended-upgrades   # ответьте «Да»: исправления безопасности ОС ставятся автоматически
```

### 2.5. Docker

```bash
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo tee /etc/apt/sources.list.d/docker.sources >/dev/null <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo usermod -aG docker deploy
```

Это официальный репозиторий Docker (для Ubuntu 26.04 он существует). Что делают команды: добавляют ключ и адрес репозитория Docker, затем ставят Docker Engine и плагин `docker compose`; последняя строка разрешает пользователю `deploy` управлять Docker без `sudo`. Короткая альтернатива, если репозиторий по какой-то причине не подходит: `curl -fsSL https://get.docker.com | sudo sh`.

Выйдите и войдите снова (`exit`, затем `ssh deploy@IP-СЕРВЕРА`), чтобы права группы применились. Проверка: `docker compose version` показывает версию 2.x.

### 2.6. Файл подкачки (если памяти 2 ГБ или меньше)

Сборка Next.js расходует много памяти. Файл подкачки страхует от аварийной остановки сборки:

```bash
sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile
sudo mkswap /swapfile && sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

### 2.7. Время

Время важно для сертификатов и журналов. `timedatectl` должен показывать `System clock synchronized: yes`. Если нет: `sudo timedatectl set-ntp true`.

## 3. DNS

В панели управления доменом создайте **A-запись**: имя `nutrition` (или то, что выбрали), значение — IP сервера. Проверка с вашего компьютера через 5–30 минут:

```bash
nslookup nutrition.mydomain.ru       # в ответе должен быть IP вашего сервера
```

Пока домен не указывает на сервер, Caddy не сможет получить сертификат.

## 4. Код на сервер

Вариант А (проще всего для первого запуска, не нужен GitHub). Упаковать папку на своём компьютере и передать по SSH. В PowerShell на Windows (программы `tar` и `scp` встроены в Windows 11):

```powershell
cd C:\Users\user\PycharmProjects\nutrition-app
tar -czf $env:TEMP\nutrition.tar.gz '--exclude=node_modules' '--exclude=.venv' '--exclude=.next' '--exclude=.git' '--exclude=.idea' '--exclude=__pycache__' '--exclude=.pytest_cache' '--exclude=.env' '--exclude=.env.local' '--exclude=uploads' '--exclude=*.dump' '--exclude=*.tar' '--exclude=*.tar.gz' .
(Get-Item $env:TEMP\nutrition.tar.gz).Length / 1MB      # размер в МБ: должно быть несколько МБ; больше 50 — в архив попало лишнее
scp $env:TEMP\nutrition.tar.gz deploy@IP-СЕРВЕРА:~/
```

Что делают команды: `tar` собирает архив, пропуская тяжёлые и секретные папки (зависимости, виртуальное окружение, историю Git, файлы `.env` с паролями, дампы базы); вторая строка показывает размер архива; `scp` копирует его на сервер в домашнюю папку пользователя `deploy`. Затем на сервере:

```bash
mkdir -p ~/nutrition && tar -xzf ~/nutrition.tar.gz -C ~/nutrition && rm ~/nutrition.tar.gz
cd ~/nutrition && ls                 # должны быть папки backend, frontend, deploy
chmod +x deploy/*.sh deploy/backup/*.sh
```

Обновление позже: повторите те же команды; файлы заменятся, а `deploy/.env` и данные (они лежат в Docker-томах) не пострадают. Удалённые вами файлы на сервере сами не удаляются; для частых обновлений удобнее Вариант Б. Пошаговое обновление с версии 1.0.0 до 1.1.0 (с копией, откатом и списком файлов, которые нужно удалить) описано в [UPDATE.md](UPDATE.md).

Вариант Б (удобнее в долгой перспективе). Репозиторий в Git на GitHub, на сервере обновление одной командой:

```bash
cd ~ && git clone https://github.com/ВАШ-ЛОГИН/nutrition-app.git nutrition
cd ~/nutrition && git pull           # при каждом обновлении
```

Если репозиторий закрытый, создайте на сервере ключ (`ssh-keygen -t ed25519`) и добавьте его в GitHub: Settings → Deploy keys. Перед отправкой в GitHub убедитесь, что в репозиторий не попали `.env`, дампы базы и архивы (они перечислены в `.gitignore`).

Файл `.env` с секретами в Git не попадает (он в `.gitignore`), его нужно создать на сервере отдельно.

Если скрипты не запускаются с ошибкой `Permission denied` (так бывает, когда код приехал с Windows и право на запуск потерялось), выдайте его один раз: `chmod +x deploy/*.sh deploy/backup/*.sh`. Сами скрипты от этого права не зависят (они вызывают друг друга через `bash`), но так удобнее запускать их командой `./deploy/deploy.sh`. Файл `.gitattributes` в корне проекта следит, чтобы скрипты и настройки сервера не получили Windows-переводы строк (`CRLF`), с которыми Linux их не выполняет.

## 5. Настройки (`deploy/.env`)

```bash
cd ~/nutrition
cp deploy/.env.example deploy/.env
chmod 600 deploy/.env          # секреты не должны читаться другими пользователями сервера
```

Сгенерируйте два разных секрета и вставьте их в файл:

```bash
openssl rand -hex 24      # → значение POSTGRES_PASSWORD
openssl rand -hex 32      # → значение JWT_SECRET_KEY
nano deploy/.env
```

Заполните: `DOMAIN`, `ACME_EMAIL`, `POSTGRES_PASSWORD`, `JWT_SECRET_KEY`, `TZ`. Остальное можно оставить как есть. Проверка:

```bash
./deploy/check-env.sh
```

Скрипт ничего не меняет, только читает файл и находит типовые ошибки: заглушки вместо секретов, слабый ключ, домен с `https://`, неправильные права файла. Ожидаемый результат: `Настройки в порядке`.

> **Сохраните `deploy/.env` в надёжном месте** (менеджер паролей). Без `POSTGRES_PASSWORD` и `JWT_SECRET_KEY` восстановить сервер из резервной копии сложнее, а если файл попадёт в чужие руки, нужно менять оба секрета (см. раздел 10).

## 6. Первый запуск

```bash
./deploy/deploy.sh
```

Что делает скрипт: создаёт папку для резервных копий, проверяет настройки, собирает образы (первая сборка 5–10 минут), запускает все службы и ждёт, пока они станут «здоровыми». В конце печатает таблицу служб и адрес сайта.

Ожидаемый результат: все службы в состоянии `running` / `healthy`, внизу строка `Готово. Сайт: https://nutrition.mydomain.ru`. Сертификат выпускается в течение минуты после запуска.

## 7. Проверка после запуска

Выполните с **вашего компьютера** (не с сервера). Замените домен на свой.

| Проверка | Команда | Ожидаемый результат |
| --- | --- | --- |
| Сайт открывается по HTTPS | `curl -sI https://nutrition.mydomain.ru` | `HTTP/2 200` (или `307` на `/login`), есть строки `strict-transport-security` и `content-security-policy` |
| http переадресует на https | `curl -sI http://nutrition.mydomain.ru` | `308` и `location: https://...` |
| API жив и видит базу | `curl -s https://nutrition.mydomain.ru/api/health` | `{"status":"ok"}` |
| Документация закрыта | `curl -s -o /dev/null -w "%{http_code}\n" https://nutrition.mydomain.ru/api/docs` | `404` |
| Схема API закрыта | `curl -s -o /dev/null -w "%{http_code}\n" https://nutrition.mydomain.ru/api/openapi.json` | `404` |
| Данные без входа не отдаются | `curl -s -o /dev/null -w "%{http_code}\n" https://nutrition.mydomain.ru/api/users/me` | `401` |

Проверка закрытых портов (с вашего компьютера; нужен `nmap`, либо на сервере `sudo ss -tlnp`): снаружи должны отвечать только 22, 80 и 443. Порты 5432 (база) и 8000 (backend) закрыты.

Затем в браузере: откройте сайт → «Зарегистрироваться» → создайте аккаунт → проверьте, что после закрытия вкладки и повторного открытия вход сохраняется (работает cookie сессии).

Оценка конфигурации HTTPS: https://www.ssllabs.com/ssltest/ (ожидается оценка A или A+).

## 8. Закройте регистрацию

Пока регистрация открыта, любой, кто знает адрес сайта, может завести аккаунт. Когда зарегистрированы все члены семьи:

```bash
nano deploy/.env          # REGISTRATION_OPEN=false
./deploy/deploy.sh        # применяет настройку (перезапускает backend)
```

Вход существующих пользователей и приглашения в семью по коду продолжают работать. Чтобы добавить нового человека, откройте регистрацию на время и закройте снова.

## 9. Обновление и откат

### Обновление

Обновление с 1.0.0 до 1.1.0 при установке архивом: [UPDATE.md](UPDATE.md). Если код на сервере берётся из Git:

```bash
cd ~/nutrition
git pull
./deploy/deploy.sh
```

Скрипт сам делает резервную копию перед пересборкой. Миграции базы применяются автоматически при старте backend. Простой сайта — около минуты.

### Откат

Если после обновления что-то сломалось:

1. Код: `git log --oneline` → `git checkout <предыдущий-коммит>` → `./deploy/deploy.sh`.
2. Если в обновлении были **миграции базы** (в `backend/alembic/versions/` появились новые файлы), одного отката кода мало: новая структура базы несовместима со старым кодом. Тогда восстановите базу из копии, сделанной перед обновлением (она создаётся автоматически): [BACKUP.md](BACKUP.md), раздел «Восстановление».

## 10. Безопасность: что уже сделано и что остаётся вам

### Защита, встроенная в приложение

| Угроза | Как закрыта |
| --- | --- |
| Подбор пароля | 5 неудачных входов на один email за 15 минут и 30 неудачных входов с одного адреса — ответ 429; время ответа не выдаёт, существует ли email |
| Массовая регистрация | 20 попыток в час с одного адреса; регистрацию можно закрыть совсем (`REGISTRATION_OPEN=false`) |
| Кража токена | Токен входа живёт 15 минут. Долгая сессия хранится в cookie `HttpOnly` + `Secure` + `SameSite=Strict`, скрипты страницы её прочитать не могут. При каждом обновлении токен заменяется; повторное предъявление украденного старого токена закрывает всю сессию |
| Чужие данные | Каждый адрес проверяет владельца и членство в семье; есть автоматические тесты, которые обходят все адреса API |
| Смена/утечка пароля | При смене пароля все старые токены и сессии на всех устройствах перестают работать сразу |
| Запросы с чужих сайтов (CSRF) | Cookie `SameSite=Strict`, проверка заголовка `Origin`, точный список разрешённых адресов CORS |
| Слишком большие запросы | Лимит 1 МБ на обычные запросы, 8 МБ на фото; дополнительно ограничение в Caddy |
| Вредоносные картинки | Проверка типа по содержимому, удаление метаданных и GPS, случайные имена файлов |
| Утечка сведений | Закрыты `/docs` и `/openapi.json`; нет заголовков с названием сервера; ответы с личными данными не кэшируются; строгие заголовки безопасности и CSP |
| Слабые настройки | В режиме production backend **не запустится**, если ключ слабый, адрес без https, не задан домен или включена документация |
| Подмена заголовка Host | Принимаются только запросы к вашему домену |
| Взлом контейнера | Службы работают с минимумом прав Linux; backend и frontend — от обычного пользователя, backend с файловой системой «только чтение»; база в отдельной сети |

### Что остаётся на вашей стороне (чек-лист)

- [ ] Вход по SSH только по ключу, root отключён (шаг 2.2).
- [ ] Файрвол включён, открыты только 22/80/443 (шаг 2.3), `fail2ban` и автообновления установлены (шаг 2.4).
- [ ] `deploy/.env` с правами 600, копия в менеджере паролей.
- [ ] Регистрация закрыта после создания аккаунтов семьи (раздел 8).
- [ ] Резервные копии делаются **и копируются за пределы сервера** ([BACKUP.md](BACKUP.md)); раз в месяц проверяется восстановление.
- [ ] Подключено оповещение о сбое копирования и о недоступности сайта (раздел 12).
- [ ] Раз в 1–2 месяца: `git pull && ./deploy/deploy.sh` (свежие версии образов) и просмотр обновлений зависимостей: `pip-audit` для backend, `npm audit` для frontend (в моей среде они не запускались из-за отсутствия доступа к реестрам пакетов).
- [ ] Пароль в приложении не короче 12 символов и нигде больше не используется.

### Ротация секретов

**`JWT_SECRET_KEY`** (раз в год или при подозрении на утечку). Замените значение в `deploy/.env` на новое (`openssl rand -hex 32`) и выполните `./deploy/deploy.sh`. Все выданные токены входа станут недействительными, но пользователи этого **не заметят**: браузер автоматически получит новый токен по cookie сессии.

**`POSTGRES_PASSWORD`**: пароль задаётся при первом создании базы и хранится в самой базе, поэтому недостаточно поменять `.env`. Порядок:

```bash
cd ~/nutrition
NEW=$(openssl rand -hex 24)
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env exec -T db \
  psql -U nutrition -d postgres -c "ALTER USER nutrition PASSWORD '$NEW'"
sed -i "s/^POSTGRES_PASSWORD=.*/POSTGRES_PASSWORD=$NEW/" deploy/.env
./deploy/deploy.sh
```

**Если `.env` или сервер попали в чужие руки**: смените оба секрета, смените пароли пользователей (смена пароля в профиле закрывает все сессии), проверьте журнал `docker compose logs`, и переустановите сервер из чистого образа, восстановив данные из копии.

## 11. Как закрыть сессии всех пользователей

Нужно при утечке или потере устройства. Все сессии разом:

```bash
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env exec -T db \
  psql -U nutrition -d nutrition -c "UPDATE refresh_tokens SET revoked_at = now(), revoked_reason = 'logout' WHERE revoked_at IS NULL"
```

Выданные токены доступа действуют не дольше 15 минут. Чтобы закрыть их немедленно, смените `JWT_SECRET_KEY` (раздел 10).

## 12. Мониторинг и обслуживание

- **Доступность сайта.** Заведите бесплатную проверку в UptimeRobot или аналогичном сервисе на адрес `https://ваш-домен/api/health` (ответ 200, если сервер жив и видит базу; 503 — если база недоступна). Оповещения придут на почту или в Telegram.
- **Состояние служб.** `docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env ps`. Все службы должны быть `healthy`. Служба `backup` становится `unhealthy`, если свежей копии нет больше суток.
- **Журналы.** `... logs -f --tail 100 backend` (или `caddy`, `backup`, `db`).
- **Диск.** `df -h` и `docker system df`. Освободить место от старых образов: `docker image prune -f`.
- **Сертификат** продлевается автоматически. Тома `caddy_data` удалять нельзя: у Let's Encrypt есть лимиты выпуска сертификатов.
- **Удобная команда.** Чтобы не набирать длинное, добавьте в `~/.bashrc`: `alias dc='docker compose -f ~/nutrition/deploy/docker-compose.prod.yml --env-file ~/nutrition/deploy/.env'` и пользуйтесь `dc ps`, `dc logs -f backend`.

## 13. Известные ограничения первой версии

Эти ограничения не мешают семейному использованию, но о них стоит знать:

- **Счётчики попыток входа хранятся в памяти процесса** и обнуляются при перезапуске backend. Для одного сервера достаточно; при нескольких экземплярах backend нужен общий Redis.
- **Токен доступа нельзя отозвать до истечения** (до 15 минут), кроме случаев смены пароля и смены `JWT_SECRET_KEY`.
- **Нет сброса пароля по почте.** Забытый пароль меняется только вручную администратором сервера. Сброс по почте можно добавить отдельным шагом.
- **Политика CSP разрешает встроенные скрипты и стили** (`'unsafe-inline'`): Next.js вставляет их в страницы. Остальные правила строгие. Полностью строгий вариант с nonce требует переделки всех страниц на динамическую отрисовку.
- **Один сервер.** Нет резервного сервера и автоматического переключения; защита данных обеспечивается копиями, а не дублированием.
- Автоматический `pip-audit` / `npm audit` не включён в процесс; запускайте вручную (см. чек-лист).

## 14. Если что-то не работает

| Симптом | Причина и решение |
| --- | --- |
| Браузер: «соединение не защищено» / не открывается | Домен ещё не указывает на сервер или закрыты порты 80/443. Проверьте DNS (шаг 3) и `dc logs caddy`: ищите строки `obtaining certificate` и ошибки Let's Encrypt |
| `dc ps`: backend перезапускается, в `dc logs backend` «Небезопасные настройки» | Сообщение перечисляет проблемы по пунктам. Исправьте `deploy/.env` и запустите `./deploy/deploy.sh` |
| Сайт отвечает «Bad Request» / 400 | Домен в `.env` не совпадает с адресом, по которому вы открываете сайт (`ALLOWED_HOSTS`) |
| Сайт открывается, но после входа сразу выкидывает | Cookie сессии не доходит: вы открыли сайт по http, а не https, или другой домен, чем указан в `DOMAIN`. Проверьте в браузере: Инструменты разработчика → Application → Cookies, у `refresh_token` путь `/api/auth` |
| «Слишком много попыток» (429) | Сработала защита от подбора пароля; подождите указанное время. Если вы за общим адресом (например, мобильная сеть) и ошибка частая, проверьте, что `TRUST_PROXY_HEADERS` включён (в нашем compose он включён) |
| Служба `backup` unhealthy | `dc logs backup`. Чаще всего папка копий не принадлежит пользователю 10001: `sudo chown 10001:10001 /var/backups/nutrition` |
| Сборка падает с «Killed» | Не хватило памяти: добавьте файл подкачки (шаг 2.6) |
| Нужно откатить или восстановить данные | [BACKUP.md](BACKUP.md) |
